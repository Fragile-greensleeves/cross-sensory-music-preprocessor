# 开发顺序与验收

采用逐阶段交付。生产流程始终保持自动运行；不把逐曲人工修正作为运行依赖。实际进度以代码、测试与报告为准，不以文档中出现工具名称视为完成集成。

| 阶段 | 交付物 | 验收条件 | 初始状态 |
|---|---|---|---|
| M0 架构与接口 | 架构图、分析方法、接口草案、来源、开发计划 | 分析目标可追溯到 Framework；每个输入/输出与失败策略明确 | 本次建立 |
| M1 音频准备 | 文件检查、WAV标准化、manifest、测试 | 晴天成功解码；保留采样率/声道；时长误差在一个采样间隔附近；不裁静音 | 本次实现与验证 |
| M2 任务框架 | 适配器接口、独立环境、任务状态、缓存、恢复、日志 | 不需人工点击；失败可重试；参数改变使缓存失效；无共享临时目录污染 | 待开发 |
| M3 即时路径 | 分轨、旋律候选选择、和弦、拍点与段落 | 晴天整曲自动生成事件；静音不伪造音高；同音重复保留；未知拍号不强填 | 待开发 |
| M4 描述路径 | 曲风、乐器、质感、段落情绪、可选文本处理 | 结构化输出通过校验；音频/歌词/背景分开；缺可选输入仍完成 | 待开发 |
| M5 统一交付 | JSON Schema、歌曲包校验器、CLI、运行报告 | 一条命令完成；秒数一致；部分失败可解释；可从缓存恢复 | 待开发 |
| M6 效果评估与下游接入 | 回放检查器、基准报告、映射读取示例 | 可对齐原曲重放事件；记录准确性/耗时/资源；交付可供Unity/其他运行端读取的数据 | 待开发 |

## 第一轮具体实施

1. 锁定《晴天》输入哈希，准备标准音频；仅记录真实元数据，不填写未经计算的 BPM、和弦或情绪。
2. 先搭建可恢复任务框架，再接 Beat This!、BTC、All-In-One，尽早验证全局时间与片段接口。
3. 接四轨分离、Basic Pitch 和 torchcrepe；先跑人声旋律，再接器乐候选和状态选择器。
4. 对前奏、人声主歌、主歌到副歌、纯器乐/静音等不同片段检查算法表现，评估策略后统一整曲重跑，不针对单曲硬编码时间。
5. 接 Essentia 与 Music2Emo；每段使用独立工作目录，保留输入上下文、原生情绪量表和推理来源。
6. 接音频描述模型与可选歌词模块；结构化字段不合规时有限重试；无资料的背景留空。
7. 完成整曲自动导出和回放报告；然后再处理视觉/灯带/马达的运行端映射与同步。

## 验证分两类

### 工程正确性（自动测试）

- 中文及带空格文件名、无音频流、损坏文件、重复输出目录。
- 音频时长、首尾静音、声道和重采样后的时间映射。
- 分段边界、补零、重叠窗口去重、事件排序及越界。
- 模型失败、断点恢复、缓存版本、生成输出的非法JSON与未知标签。
- 缺歌词/背景时 skipped，不阻塞音频路径；任何假数据只用于标明的单元测试，不混入实测报告。

### 音乐效果（离线评估，不加入生产审批）

- 旋律：音高/八度错误、发声检测、音符起止、同音重复与声部切换。
- 和声：区间加权标签一致性，复杂和弦和 unknown/no_chord 的区分。
- 节奏：拍点/第一拍准确性、半倍速错误和连续性。
- 段落：边界误差与功能标签；无真值时只做诊断，不发布虚构准确率。
- 描述：字段合法性与语义效果分别评估；情绪标签是模型估计，不当作听障观众的真实体验。
- 速度：记录机器、运行环境、CPU/GPU、模型版本、峰值资源、每阶段耗时，不提前承诺实时或处理时长。

《晴天》是首个集成样本，不能独自证明泛化。稳定后加入其他风格和无主唱片段；有标注的数据用于定量评估，无标注的歌曲用于运行和错误诊断。

## 开发约定

- 每个阶段用独立分支和小型提交，文档同步更新实际状态；初始文档与基础脚本发布在 main。
- 当前自动测试在本地执行；Actions 配置保存为普通示例文件。云端 CI 待具备工作流写权限后再启用，不将示例文件视为已运行的 CI。
- 大模型依赖按 worker 隔离；从上游文档验证可用 Python/运行时，再记录环境锁定文件，不在未验证时宣称兼容。
- 预训练模型首次运行先验证下载和加载，再登记权重来源、哈希、许可与版本。
- 音频、完整歌词、分离声部、模型权重留在本地，提交代码、文档、无音频的运行指标和必要样例。
- 当前没有完整训练或微调计划；先用预训练模型验证，只有明确失败模式与数据后再考虑训练。
